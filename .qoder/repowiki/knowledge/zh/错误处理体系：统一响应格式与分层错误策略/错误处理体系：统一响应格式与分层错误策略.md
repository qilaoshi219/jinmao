该项目的错误处理采用前后端分离的分层策略，后端基于 Express 框架，前端使用 Axios 拦截器，形成统一的错误处理机制。

**后端错误处理架构**

- **全局错误中间件**：在 `node-jinmao/app.js` 中注册了 Express 的错误处理中间件 `(err, req, res, next)`，捕获所有未处理的异常并返回统一的 `{code: 500, message: "服务器内部错误"}` 格式响应。404 路由也通过专门的中间件处理，返回 `{code: 404, message: "Not Found"}`。
- **启动前自检**：应用启动时执行严格的依赖检查（.env 文件、环境变量、Prisma Client 生成、数据库迁移），任何关键依赖缺失都会输出详细的中文错误提示并退出进程，避免带病运行。
- **HTTP 状态码映射**：每个 API 路由都维护 `statusMap` 对象，将业务层的 code（200/400/401/403/429/500）映射到对应的 HTTP 状态码，确保语义清晰。
- **JWT 鉴权中间件**：`middleware/auth.js` 中的 `authenticateToken` 中间件统一处理 Token 验证失败的情况，直接返回 401 响应，不进入业务逻辑。
- **进程级异常保护**：注册了 `uncaughtException` 和 `unhandledRejection` 处理器，记录详细堆栈但不退出进程，保证服务稳定性。

**前端错误处理策略**

- **Axios 拦截器**：`WEB/src/api/client.js` 配置了请求和响应拦截器。请求拦截器自动附加 JWT Token，响应拦截器统一处理 401 未授权错误（清除 token 并重定向登录页）和网络错误。
- **try-catch 包裹**：各页面脚本中使用 try-catch 包裹异步操作，捕获具体错误并进行用户友好的提示。

**统一响应格式**

所有 API 响应遵循一致的 JSON 结构：`{code: number, message: string, data?: any}`，其中 code 表示业务状态码，message 提供人类可读的错误描述，data 包含成功时的数据负载。

**错误传播模式**

- Service 层返回 `{code, message, data?}` 对象而非抛出异常
- API 层根据 code 映射 HTTP 状态码并返回响应
- 前端通过 Axios 拦截器统一处理网络层错误
- 业务错误通过 code 字段区分，非业务错误通过 HTTP 状态码区分
