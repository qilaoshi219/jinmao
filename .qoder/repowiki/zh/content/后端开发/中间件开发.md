## 架构总览
Express 的请求处理模型基于“中间件链”。每个中间件可读取/修改 req/res，决定是否继续调用下一个中间件或提前结束响应。错误处理中间件通过四个参数的函数签名被识别，并在错误发生时接管流程。

```mermaid
sequenceDiagram
participant Client as "客户端"
participant App as "Express 应用"
participant MW1 as "通用中间件(日志/CORS)"
participant MW2 as "认证中间件"
participant Route as "路由处理器"
participant Err as "错误处理中间件"
Client->>App : HTTP 请求
App->>MW1 : 进入中间件链
MW1-->>App : 继续/终止
App->>MW2 : 认证检查
alt 认证失败
MW2-->>Err : 抛出错误
Err-->>Client : 统一错误响应
else 认证成功
MW2-->>Route : 继续到路由
Route-->>Client : 业务响应
end
```

## 详细组件分析

### 认证中间件（Auth Middleware）
职责
- 从请求头或 Cookie 中提取凭证（如 JWT）
- 校验签名、过期时间、权限范围
- 将用户信息挂载到 req.user，供后续路由使用
- 失败时返回标准错误响应或抛出错误交由错误处理中间件处理

实现要点
- 优先放在路由之前，确保受保护接口均经过鉴权
- 支持白名单路径跳过鉴权（如登录、健康检查）
- 对异常进行统一捕获并转换为标准错误格式

```mermaid
flowchart TD
Start(["进入认证中间件"]) --> ReadToken["读取令牌/会话"]
ReadToken --> HasToken{"存在有效令牌?"}
HasToken --> |否| Deny["拒绝访问/返回未授权"]
HasToken --> |是| Verify["验证签名/有效期/权限"]
Verify --> Valid{"校验通过?"}
Valid --> |否| Deny
Valid --> |是| AttachUser["挂载用户信息到请求对象"]
AttachUser --> Next["调用下一个中间件/路由"]
Deny --> End(["结束"])
Next --> End
```

### 错误处理中间件（Error Handler）
职责
- 捕获同步/异步异常
- 区分业务错误与系统错误
- 统一错误码、消息、堆栈（生产环境隐藏敏感信息）
- 记录错误上下文（请求ID、URL、方法、用户、耗时）

关键点
- 必须具有四个参数 (err, req, res, next) 才能被 Express 识别为错误处理中间件
- 避免在错误处理中间件中再次抛出未捕获异常
- 保持幂等性，防止重复写入响应

```mermaid
flowchart TD
Enter(["错误处理中间件"]) --> CheckStatus{"是否已有状态码?"}
CheckStatus --> |有| UseExisting["沿用已有状态码"]
CheckStatus --> |无| SetDefault["设置默认错误状态码"]
SetDefault --> BuildResp["构建统一错误响应体"]
UseExisting --> BuildResp
BuildResp --> LogErr["记录错误日志与上下文"]
LogErr --> Send["发送响应"]
Send --> Exit(["退出"])
```

### 参数验证中间件（Validation Middleware）
职责
- 校验请求体、查询参数、路径参数、头部字段
- 提供清晰的错误提示与字段级错误
- 支持自定义校验规则与异步校验（如唯一性检查）

建议
- 使用独立的校验中间件，按路由粒度复用
- 将校验失败直接返回 4xx，不进入业务逻辑
- 结合类型定义（如 TypeScript）提升可维护性

```mermaid
flowchart TD
VStart(["进入验证中间件"]) --> Parse["解析输入"]
Parse --> Validate["逐项校验规则"]
Validate --> AnyFail{"是否存在错误?"}
AnyFail --> |是| Return400["返回参数错误"]
AnyFail --> |否| Pass["放行至下一中间件/路由"]
Return400 --> VEnd(["结束"])
Pass --> VEnd
```

### 日志记录中间件（Logging Middleware）
职责
- 记录请求方法、路径、IP、UA、耗时、状态码
- 可选记录请求/响应体（注意脱敏）
- 输出结构化日志，便于聚合与分析

建议
- 使用请求 ID 贯穿全链路
- 控制日志级别与采样率，避免影响性能
- 对大体积响应体仅记录摘要

### 性能监控中间件（Performance Monitoring）
职责
- 统计关键接口的 P50/P95/P99 延迟
- 暴露指标端点（如 /metrics）供监控系统采集
- 记录慢请求与异常热点

建议
- 使用直方图或计数器聚合指标
- 避免在热路径中进行昂贵操作

### 请求拦截器（Request Interceptor）
职责
- 在路由前对请求进行预处理（如埋点、灰度、限流、缓存命中）
- 可改写请求体或头部（谨慎使用）
- 快速失败场景（如黑名单 IP、配额不足）

HitCache --> |否| Proceed["继续后续处理"]

### 中间件组合模式与异步处理
- 组合模式：通过模块化拆分中间件，按需组合；可使用高阶函数封装通用逻辑（如重试、超时、缓存）。
- 异步处理：使用 async/await 或 Promise，确保错误通过 next(err) 传递；避免忘记调用 next() 导致挂起。

```mermaid
sequenceDiagram

participant Auth as "认证中间件"
participant Cache as "缓存中间件"

Client->>Chain : 请求

Auth-->>Chain : 成功/失败
alt 失败
Chain-->>Client : 错误响应
else 成功
Chain->>Cache : 尝试缓存命中
alt 命中
Cache-->>Client : 缓存响应
else 未命中
Cache->>Handler : 执行业务逻辑

end
end
```

## 性能考虑
- 中间件顺序：将轻量且高频的中间件（如 CORS、日志）前置，重逻辑后置。
- 避免阻塞：I/O 操作务必异步化，减少同步阻塞。
- 缓存策略：对读多写少的接口启用缓存，降低下游压力。
- 资源限制：合理设置请求体大小、并发数、超时时间。
- 指标观测：接入延迟、吞吐、错误率等关键指标，持续优化。

## 故障排查指南
- 确认中间件顺序：检查是否在认证前误放需要鉴权的中间件。
- 检查 next() 调用：遗漏 next() 会导致请求挂起。
- 错误处理中间件位置：必须在所有路由之后注册。
- 日志与追踪：开启请求 ID 与结构化日志，定位问题链路。
- 性能瓶颈：通过监控中间件定位慢接口与热点路径。
- 常见错误：
  - 401/403：认证失败或权限不足
  - 400：参数校验失败
  - 500：服务端异常，查看错误日志与堆栈
